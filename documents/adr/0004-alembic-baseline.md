# ADR-0004: Alembic is the single schema authority with a domain baseline

- Status: Accepted
- Date: 2026-11-20
- Plan: documents/plans/2026-11-20-colombus-persistence-migration.md

## Context

Persistences's scaffold shipped a demo **`User`/`Item`** model plus a
five-migration Alembic chain (initialize → timestamps → column length → UUID
→ cascade FKs) that only ever described that throwaway scaffold. Colombus has
no Alembic at all: it auto-creates tables with `SQLModel.metadata.create_all`
in its lifespan. Persistence must take over schema ownership and describe the
eight real domain tables with versioned migrations.

## Decision

- `app/alembic/env.py` now targets `app/db/models.py`'s metadata
  (`SQLModel.metadata`), not the demo `app.models`.
- The demo `User`/`Item` migration chain is removed and replaced with a **single
  baseline migration** (`19aacbaabe42`) that `CREATE TABLE`s all domain tables —
  `project`, `pattern`, `profile`, `matchingprofile`, `step`, `celloutput`,
  `metainstruction`, `code` — with the composite PK on `matchingprofile`,
  CASCADE FKs and the `ix_step_profile_id_position` index, generated by
  `alembic revision --autogenerate`.
- `env.get_url()` honours an `ALEMBIC_DATABASE_URL` override so tests can run
  migrations against a dedicated DB; otherwise it falls back to
  `settings.DATABASE_URL`(LOCALHOST).

## Consequences

- Migrations become the single source of truth for the shape of the DB; the
  models and the migration must agree, enforced by a test that upgrades a fresh
  DB to head and asserts the resulting table set equals the model metadata.
- Colombus can stop calling `create_db_and_tables()` once it is pointed at
  persistence's schema (handled in the strangler sequencing).
- Any future schema change is a new migration appended after this baseline,
  giving a clean, reviewable history.
